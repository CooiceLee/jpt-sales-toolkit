覆盖升级：先保护旧数据

升级前留基线

完全退出旧版，记录客户与询盘总数，并打开一条原附件确认可读。不要复制正在运行的 SQLite 文件。

让新版自动备份

新版第一次识别到旧 schema 时，会先在本机 data/backups 创建并验证 pre_upgrade_...zip，随后才迁移。备份包含数据库、附件和授权配置，不包含桌面锁等瞬时文件。

验证升级结果

使用原账号登录，核对总数、负责人、阶段、跟进和至少一个原附件；完全退出并第二次启动，再核对一次。第二次启动不应再创建同一次升级备份。

失败时停止并恢复

迁移或校验失败会自动恢复原数据库并停止启动。不要删除数据目录或反复安装；保留提示和 launcher.log。管理员可从已安装程序运行 --recover-backup "<pre_upgrade...zip>"，无需源码环境。入口只接受系统自动生成的 pre_upgrade ZIP，不接受普通完整备份；替换前会先保存当前数据库为 pre_recovery_current_*.sqlite，成功或失败都会显示明确结果。

升级保护是安装 Gate，不是 Excel Gate。自动 pre-upgrade 备份只保护程序 schema 升级；Excel 正式导入前仍需在向导第 1 步另建完整备份。

1. 建立账号、设备授权和业务地区

全新团队的首位 Leader

  1. 选择建立新团队，设置 Leader 用户名和本地登录密码。
  2. 设置至少 12 位签发器口令；口令不写入数据库且无法找回。
  3. 系统生成签发密钥并绑定当前设备 90 天。
  4. 立即创建完整备份，把备份与签发器口令分开保存。

为成员签发

  1. 先创建成员，角色只能为 Leader / Sales / Tech。
  2. 接收成员本机生成的 .jptreq。
  3. 核对姓名、设备和角色后签发 .jptauth。
  4. 授权文件与 16 位验证码通过两条可信渠道发送。
每名成员默认一台设备。换机时由新电脑重新生成申请并重签；旧授权成为历史。当前离线模式不承诺设备丢失后立即远程停用。

应用修正并重新预检可以导入导入并合并

进入正确页签

用 Leader 登录，进入“导出 / 导入”，选择顶部“Excel 导入”。JSON、数据治理和客户合并在独立页签，不要混用。

  • 没有 Excel 页签：核对角色与版本。
  • 看到旧版左右卡片：完全退出旧程序并从正确安装副本重开。

创建完整备份

先点击“创建完整备份”，等待成功并记录文件名、时间和保存位置。JSON 的“导出我的数据”不包含附件，不能代替完整备份。

  • 备份失败或没有记录位置：停止导入。
  • 备份包含授权配置，应按敏感文件保管。

选择工作簿

点击“选择工作簿”，选择需要导入的 .xlsx，确认页面文件名正确。工作表名称和前四行结构不得改变，业务数据从第 5 行开始。

  • 不接受 .xls、.xlsm、空文件或超限文件。
  • 预检后不要覆盖、重新保存或替换原文件。

运行只读预检

点击“运行预检”。预检只解析文件和生成报告，不写数据库。先核对源数据行、实体、错误和警告数量。

  • 错误：阻断提交，必须修复、映射或确认排除。
  • 警告：允许提交，但导入后要人工补充或核验。
  • 信息：来源追踪或自动匹配说明。

处理成员账号映射

展开成员分组，把来源姓名、缩写和大小写变体映射到实际启用账号。工作簿不能创建账号。

  • Lead owner 只能映射到 Leader 或 Sales。
  • 售前/售后任务 assignee 只能映射到 Tech。
  • 同一来源姓名按 owner、collaborator、actor、task assignee 等职责可能要分别选择账号。
  • 未知、停用、歧义或角色不匹配均为阻断项。

处理客户匹配

展开客户分组，核对主名称、别名、国家、域名和联系人。确认是同一客户时选择现有目标；不是同一实体时创建新客户。

  • 名称相似不代表实体相同。
  • 只有确认源记录无效时才排除，不能为了让按钮可用而随意排除。
  • 预检匹配不修改原 Excel。

应用修正并重新预检

修改过账号、客户或排除项后，点击“应用修正并重新预检”。只有显示“可以导入”且阻断项为 0 时才能提交。

  • 仍显示阻断数量：继续处理对应分组。
  • 文件有任何变化：重新选择并从预检开始。

执行一次正式提交

再次核对文件、数据集和映射，点击一次“导入并合并”。成功后记录批次编号以及新增、更新、归档、跳过和警告数量。

  • 明确失败：整批回滚，不保留半批数据。
  • 显示“结果无法确认”：不要立即重试；重开程序先查左侧计数和目标记录。
  • 明确显示导入完成但导航刷新失败：不要重复导入，只需重开页面核对。

验证幂等更新与权限

第二次导入完全相同文件，不应新增副本；再保留原稳定键只修改一个允许字段，确认仅更新目标记录。

  • 分别用 Leader、目标/非目标 Sales、目标/非目标 Tech 核对可见范围。
  • 检查警告记录是否在对应卡片中可见并可人工补充。
  • 检查负责人业务地区、跟进时间、样品/任务和地图质量是否正确。

3. 地区与长期未跟进的组合筛选

计划到期

“已逾期 / 今日到期 / 未来 7 天”只看下一次计划跟进日期。没有计划日期的记录不应被当作逾期；空状态应说明是缺少计划日期、没有符合范围的记录，还是组合条件过窄。

长期未跟进

活动日期按“最近正式跟进 → 询盘日期 → 创建日期”回退。可选择未跟进时间门槛，找出长期没有实际跟进的卡片；“从未正式跟进”仅表示没有正式跟进活动。

组合条件取交集。业务地区、负责人、技术人员、搜索词、计划到期和长期未跟进条件会同时缩小结果。页面为 0 时先逐项核对当前条件；清除地区应选择“全部地区”，不是 GLOBAL。

4. 客户名称/别名模糊候选与一键合并

搜索候选

进入“客户合并”，输入法律名称、品牌名、简称或历史名称。候选同时检索主名称和别名，并显示相似度分数及匹配来源。

选择来源与保留目标

来源客户是将被归档的重复实体，目标客户是合并后保留的实体。核对国家、域名、联系人、Lead 和历史记录，不要只看分数。

核对只读迁移预览

选择两端后等待预览。核对将迁移的联系人、Lead、域名、别名和其他受支持关联；预览本身不写数据。

执行一次合并并复核

预览有效且目标正确后只点击一次合并。来源客户归档，关联迁移到目标并保留审计。完成后用两个名称重新搜索，核对目标别名、联系人和 Lead。

不能合并的情况：只是名称近似但法律实体不同、国家/域名冲突无法解释、预览缺少预期关联、来源与目标选反、数据正在由其他导入批次修改。此时保留两个客户并补充别名或人工说明。

5. 地图与坐标质量

状态可以做什么不能据此做什么
精确显示经过确认的经纬度；用于地图定位与复核仍不能代替拜访前核对实际地址和联系人
近似显示国家、城市或区域级参考位置不能作为楼宇定位、路线终点或精确距离依据
缺失进入坐标复核，填写地址、城市、邮编和国家后搜索候选，也可地图选点或人工输入经纬度不能把没有坐标的客户从业务清单中视为不存在
地址搜索先选候选再保存。同一地址可能返回多个结果，应核对完整地址、国家和坐标后人工确认；自动候选只保留为待复核，不会自动覆盖已确认位置。地址字段会发送给一个或多个外部服务；高德发生空结果、网络、超时、配额或无效响应时会回退 Nominatim，界面显示实际候选服务商。Key/权限错误不会被回退掩盖。不允许外发的地址必须改用人工经纬度或地图选点。
高德是可选地理编码，不内置 Key，也不替换底图。管理员必须在启动程序前提供 JPT_GEOCODING_PROVIDER=amap 和服务端 Web Service Key JPT_AMAP_WEB_SERVICE_KEY。高德坐标会转换为统一 WGS84；底图仍访问 CARTO/OpenStreetMap。公共 Nominatim 只用于小规模、单终端、一次性查询。Key 不得写入前端、GitHub、安装包、截图、文档、启动脚本或日志。

Windows 开始菜单启动

由管理员把两个变量写入受控的当前用户系统环境，随后退出 Windows 账号并重新登录，再从开始菜单启动 JPT。只在已经打开的 PowerShell 窗口中设置变量，不会传给正在运行的 Explorer。

macOS Finder 启动

由管理员通过 launchd 或 MDM 向当前 GUI 会话注入两个变量，完全退出 JPT 后再从“应用程序”启动。普通 Terminal 中的临时 export 不会传给 Finder；重启或重新登录后须按组织配置重新确认。

验证与回退

只使用不敏感测试地址，确认返回服务商及候选正常。当前版本没有 Key 输入界面；无法完成受控系统配置时保持 Nominatim，不要让成员复制 Key 或把 Key 写入共享文件。

6. 0.11.7 界面操作快查

左上角全局搜索

输入至少两个字符，在当前账号权限范围内搜索询盘编号、客户、联系人或国家。使用上下方向键选择、Enter 打开、Esc 关闭；Tech 只会跳转到其允许访问的任务模块。

卡片与右侧详情

点击卡片后，当前卡片会保持明显选中状态，右侧标题同时显示询盘编号和客户。切换卡片前若表单有未保存修改，系统会要求确认。

数据质量角标

卡片显示待复核数量时，右侧“数据质量”标签也显示相同角标；解决、忽略或重新打开后两处同步更新。角标为 0 时隐藏。

筛选与空页面

状态、搜索、销售、技术和地区在同一对齐工具栏内，组合条件取交集。接口失败会显示错误和重试，不会伪装成“没有记录”；真正为空时再按页面说明放宽条件。

7. JSON 数据包终端同步

Leader → Sales 正确流程

  1. 发送端先创建完整备份。
  2. 进入“JSON 数据交换”，从接收成员下拉框选择目标 Sales。
  3. 导出后记录目标成员、时间、版本、文件名和记录数；新包只包含该成员作为负责人的 Lead。
  4. 目标 Sales 对所选文件运行预检，核对源总数、允许数、权限跳过数、错误和冲突；其他成员导入同一包应被拒绝。
  5. 只有同一文件错误数为 0、权限跳过数为 0 时按钮才可提交；更换文件会使预检失效，必须重新预检。
  6. 执行合并后确认结果是完整成功而非部分完成，再核对客户、Lead、主联系人、活动和任务。
  7. 重复导入同一包，确认不新增重复记录且本地活动仍保留；Sales 回传 Leader 时应更新原 Lead，不建立来源副本。

边界与异常

  • Excel 用于外部/历史数据摄取，不是持续同步协议。
  • JSON 只包含附件元数据，附件本体独立传递。
  • 完整备份不是普通成员同步包。
  • .jptauth、.jptreq 不进入业务同步目录。
  • 不要把 Leader 全量包改名后发送；应重新选择目标成员导出。
  • 旧版无接收成员字段的包仍会逐条做权限过滤；不能用它证明新版定向分发已通过。
  • 单条异常会回滚该记录及其从属联系人，不应留下半写入实体。
