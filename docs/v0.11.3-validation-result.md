# JPT Sales Toolkit 0.11.3-internal 本地候选验证结果

验证日期：2026-07-16
状态：Intel macOS 本地候选已通过；尚未提交或推送 GitHub，Windows 与 Apple Silicon 安装包尚未构建。

## 故障结论

- `0.11.2-internal` 页面出现的 `Failed to fetch` 不是工作簿格式校验结果，而是本地后端进程已经停止。
- macOS 诊断报告记录 `EXC_BAD_ACCESS / SIGSEGV`，调用栈进入 `sqlite3DbMallocRawNN -> sqlite3VdbeMemGrow -> sqlite3VdbeExec -> sqlite3_step -> _sqlite3`。
- 实际数据目录的 SQLite `integrity_check` 与 `quick_check` 均为 `ok`；故障发生时业务表仍为 0 条，当前工作簿没有完成预检或写入。
- 相同冻结程序配合原工作簿和隔离数据目录不能稳定复现原生崩溃。因此不能把唯一根因断言为某一条业务数据；本版针对已证实的跨线程共享连接风险做防御性加固。

## 本轮修复

- Excel 预检和提交改用请求级独立 SQLite 连接，所有退出路径都关闭连接。
- 数据库初始化和关闭增加进程内锁，关闭 SQLite statement cache，并统一启用外键与 5 秒 busy timeout。
- 授权依赖改为异步依赖，避免在 AnyIO worker 创建含数据库连接的服务后再跨线程使用。
- 前端捕获网络断连并二次探测 `/api/health`；预检断连时明确提示“当前工作簿尚未导入”，不再显示原始 `Failed to fetch`。
- 正式提交断连或响应无法解析时不再声称“未导入”，而是保持文件和预检报告、锁定再次提交，并提示结果无法确认；需重开 JPT 后核对左侧计数和目标业务记录。
- 服务已返回成功结果后，即使后续导航计数刷新失败，也会先固定“导入完成”状态并禁止重复提交；界面只提示重新打开 JPT 加载最新计数。
- 预检和提交期间统一锁定工作簿选择器及全部相关动作；选择纪元、请求令牌和 File 对象身份共同阻止同名、同大小、同时间戳文件的旧响应覆盖新选择。
- 冻结应用烟测新增真实 multipart XLSX 预检，并在预检后再次验证服务健康和进程存活。

## 已通过

- 完整源码回归：`bash scripts/validate_v08.sh` 通过，覆盖 Python 编译、JavaScript 语法、三角色权限、授权、备份恢复、JSON 数据交换、XLSX 解析/预检/提交、客户合并、数据质量和前端模块契约。
- 等价真实工作簿：冻结 `0.11.3-internal` 接口预检返回 200，识别 1621 个候选实体、121 个错误、137 个警告和 64 项成员映射；预检后 `/api/health` 仍为 `ok`，进程保持存活。源文件名和本机路径已从公开验证记录中移除。
- 本轮真实工作簿仍存在阻断项，`can_commit=false`，所以没有执行正式写入；原工作簿也未被修改。
