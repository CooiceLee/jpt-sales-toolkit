# JPT 销售数据标准导入格式

当前标准版本：`JPT-XLSX-1.0`

## 1. 适用范围

标准工作簿作为独立文件分发，用于在 JPT Sales Toolkit 安装和账号激活完成后导入客户、联系人、商机、协作成员、互动记录、售前任务和售后任务。安装包不内置 XLSX。JSON 导入仍用于成员终端之间的数据交换；XLSX 仅用于 Leader 集中整理历史或外部数据，不作为终端同步协议。

导入固定执行以下链路：

1. 上传文件并解析，不写数据库。
2. 预检字段、枚举、关联关系、成员账号、重复客户和潜在数据缺口。
3. Leader 处理阻断项：选择实际账号、确认客户匹配或排除无效记录。
4. 再次校验文件哈希，确认文件未在预检后被替换。
5. 单批次提交；失败时整个批次回滚。
6. 保存来源绑定和质量提示，重复导入相同外部键时更新原记录。

## 2. 工作簿结构

不得修改工作表名称或首四行结构。业务数据从第 5 行开始。

| 工作表 | 一行代表 | 主外部键 | 主要关联键 |
|---|---|---|---|
| 客户 | 一个客户 | `customer_key` | — |
| 客户别名 | 一个客户名称变体 | `alias_key` | `customer_key` |
| 联系人 | 一名联系人 | `contact_key` | `customer_key` |
| 商机 | 一条商业机会 | `lead_key` | `customer_key`, `primary_contact_key` |
| 商机协作成员 | 一名协作成员 | `assignment_key` | `lead_key`, `member_username` |
| 互动记录 | 一次跟进或评论 | `activity_key` | `lead_key`, `actor_username` |
| 售前任务 | 一名成员承担的一项任务 | `task_key` | `lead_key`, `assignee_username` |
| 售后任务 | 一名成员承担的一项任务 | `task_key` | `lead_key`, `assignee_username` |

`_成员目录`、`_枚举字典`、`_来源追踪`、`_校验结果` 是辅助表。辅助表名称以 `_` 开头，不应被当作业务数据表编辑或另存为单独文件。

## 3. 外部键与重复导入

- `dataset_id` 标识一套持续维护的数据集，同一数据集后续更新必须沿用原值。
- 所有 `*_key` 在同一 `dataset_id` 内必须唯一且永久稳定。
- 不得使用 Excel 行号作为键；推荐使用原系统 ID，若无原 ID，可使用稳定业务编码。
- App 以 `dataset_id + entity_type + external_key` 记录本地绑定。重复导入会更新已绑定记录，不会再创建一份副本。
- 把同一份数据改用新的 `dataset_id` 会被视为新的数据集，可能产生重复记录。

## 4. 操作语义

每张业务表的 `action` 仅接受以下值：

| 值 | 含义 |
|---|---|
| `UPSERT` | 不存在则创建，已绑定则更新 |
| `ARCHIVE` | 归档已绑定记录，不物理删除 |
| `RESTORE` | 恢复已归档记录 |
| `SKIP` | 本次忽略该行 |

更新已有记录时，空白单元格表示“不修改原值”；需要显式清空字段时填写 `__CLEAR__`。必填关系键不得清空。

## 5. 账号与权限

- 工作簿不能创建账号；账号必须先由 Leader 在授权中心建立并保持启用。
- `owner_username` 只能匹配有效的 Leader 或 Sales 账号。
- `assignee_username` 用于售前/售后任务时只能匹配有效的 Tech 账号。
- `actor_username` 和 watcher 可以匹配 Leader、Sales 或 Tech。
- 来源文档中的姓名、缩写和大小写变体先与成员导入别名匹配；无法唯一匹配时必须由 Leader 选择实际账号。
- Leader 确认的姓名映射会作为该来源系统的成员别名保存，供后续导入复用。

任何未知账号、停用账号、歧义账号或角色错配都是阻断项，不能静默改给当前导入人。

## 6. 客户别名与合并

- 大小写、全半角和多余空格差异会参与规范化匹配，但不会直接物理合并客户。
- 同一客户的法律名称、品牌名、简称或历史名称应写入“客户别名”表。
- 预检给出唯一精确匹配时可复用现有客户；出现多个候选时由 Leader 选择目标客户或确认新建。
- 已存在的重复客户使用 App 的客户合并预览，确认联系人、商机、域名和别名迁移结果后执行软合并。
- 合并必须保留来源记录和审计信息；不得通过改名掩盖两个客户实体。

## 7. 字段和值

- 日期统一使用 `YYYY-MM-DD`，日期时间使用 `YYYY-MM-DD hh:mm`。
- 金额列只写数值，币种单独填写 `currency`。
- 枚举值从 `_枚举字典` 选择；不得用颜色、字体或隐藏行表达业务状态。
- 一个客户最多只有一个 `is_primary=TRUE` 的联系人。
- 一条商机可以有多个协作成员；owner 只在“商机”表填写。
- 售前或售后多人协作时，每名成员单独一行，并共享同一 `task_group_key`。

## 8. 数据缺口与人工修正

预检问题分为三类：

- `error`：阻断提交，例如缺少客户、商机标题、外部键、负责人，或关系键不存在。
- `warning`：允许提交但会在 App 中保留质量提示，例如来源日期无法可靠解析、业务备注未能拆分到结构化字段。
- `info`：来源追踪或自动匹配说明。

Leader 可以在预检界面完成以下修正：

- 把来源人员名称映射到实际账号；
- 把来源客户匹配到现有客户，或确认新建；
- 排除确认无效的来源记录；
- 对可接受的数据缺口保留质量提示，后续在 App 中人工补齐。

自动解析或匹配结果必须可修改，且不会反向覆盖原始 Excel 文件。成员别名和数据集实体绑定会保留供后续导入复用；排除记录等选择仅作用于当前批次。

## 9. 来源追踪

兼容旧版彩色工作簿时，App 会读取工作表、源行号、填充色、隐藏状态和原始日期文本用于追踪。颜色只作为来源证据，不直接决定销售阶段或业务状态。

标准工作簿中的 `_来源追踪` 表可携带外部系统的来源记录键、文件哈希和原始备注。正式提交后，App 还会保存导入批次、外部键绑定和未解决的数据质量提示。

## 10. 文件安全边界

- 仅接受 `.xlsx` 和既有 JSON 数据交换包，不接受含宏的 `.xlsm`。
- App 单次上传的 XLSX 最大 25 MB；解析器还会限制压缩包成员数量、展开体积和压缩比。
- 不执行公式、宏、外部链接或嵌入对象。
- 文件在预检和提交之间发生变化时，提交会被拒绝，必须重新预检。
