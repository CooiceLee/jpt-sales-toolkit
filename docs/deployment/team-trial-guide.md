# JPT Sales Toolkit 团队试装与独立模块验收手册

适用版本：`0.11.8-internal`。产品只维护 Windows 10/11 x64、macOS Apple Silicon arm64 和 macOS Intel x86_64。本版本是加入 Tech 任务包的 `UNSIGNED-INTERNAL` 团队测试 / Pre-release。原生三平台门禁和团队实测全部通过前，既有稳定基线仍为 `v0.11.7-internal`，不得用本候选替代。

## 1. 验收原则

团队试运行分为四个独立模块：程序安装、外部 XLSX 导入、账号权限映射、终端数据包同步。每个模块使用独立输入、独立证据和独立结论。安装包不得预装业务 Excel、成员授权、业务数据库或测试业务数据。

推荐测试顺序：

1. Gate A：纯净安装、激活、基础操作和本地数据持久化。
2. Gate B：在 Gate A 通过后的程序中单独导入和更新 XLSX。
3. Gate C：使用真实测试账号核对导入后的权限划分。
4. Gate D：在两个独立终端数据目录之间，分别验证 Sales JSON 与 Tech 任务包同步。

任何 Gate 出现 P0 或 P1 问题时停止进入下一 Gate，先保留日志、截图和测试前备份。

## 2. 分发文件边界

公开给所有测试成员的文件只有其电脑架构对应的安装包、成员安装指南和 SHA-256 校验文件。Leader 单独保管标准 XLSX、测试源文件、账号清单、签发器口令、`.jptauth`、完整备份和同步数据包。

- 安装包：统一程序，不区分 Leader / Sales / Tech。
- `.jptreq`：成员设备请求，可发送给 Leader。
- `.jptauth`：Leader 针对成员和设备签发，必须点对点发送。
- XLSX：外部数据摄取文件，只由 Leader 预检和提交。
- Sales JSON：Leader / Sales 终端之间的 Lead 交换包，不等同于完整备份。
- `.jpttask`：Leader 选定精确 Tech 账号后导出的技术任务分配包。
- `.jptresult`：Tech 保存任务更新后回传给 Leader 的结果包。
- 备份 ZIP：包含数据库、附件和授权配置，按敏感文件管理。

`.jpttask` 和 `.jptresult` 内部是 JSON 格式，但必须使用独立“Tech Task Packages / 技术任务包”页签，不能在 Sales JSON 页签导入。首版有内容校验和精确接收账号校验，但尚无设备数字签名；两类包只通过团队批准的可信内部渠道点对点传递。

## 3. Gate A：纯净安装与基础程序

### 3.1 安装前

1. 根据设备选择 Windows x64、macOS arm64 或 macOS x86_64 安装包。
2. 使用 `SHA256SUMS.txt` 核对安装包哈希。
3. 确认测试电脑没有复制旧版 `data` 目录；升级测试除外。
4. 确认没有把 XLSX、`.jptauth` 或业务数据库放入安装目录。

### 3.2 Windows

运行 Setup EXE。若 SmartScreen 提示未知发布者，只在文件名和 SHA-256 均与 Leader 提供记录一致时选择“更多信息 → 仍要运行”。默认安装到当前用户目录，不要求管理员权限。

### 3.3 macOS

打开对应架构的 DMG，把 JPT Sales Toolkit 拖入 Applications，随后推出 DMG，并从 Applications 打开。不要直接运行 DMG 内的 App；新版检测到从只读磁盘映像运行时会显示安装位置警告。当前内部包未做 Apple notarization；若 Gatekeeper 阻止首次打开，在 Finder 中按住 Control 点击应用并选择“打开”，再次确认。不要使用来源不明的终端命令绕过系统安全策略。

### 3.4 首次激活

- 首位 Leader 选择 `Set up a new team`，设置登录密码和至少 12 位签发器口令，随后立即生成完整备份。
- 已有成员选择 `Join an Existing Team`，下载 `.jptreq`，发送给 Leader。
- Leader 签发 `.jptauth`，授权文件和 16 位验证码必须通过两条不同可信渠道发送。
- 成员导入 `.jptauth`、输入验证码、设置本地密码并登录。

### 3.5 Gate A 通过标准

- `/api/health` 显示正确版本并只监听 `127.0.0.1`。
- Leader、Sales、Tech 均可按授权登录。
- 新建一条带唯一测试标识的客户或 Lead，退出程序并重启后仍存在。
- `Exit JPT` 能停止后台程序，覆盖升级不丢数据。
- 卸载不删除用户数据目录；完整备份能够恢复数据库、附件和授权配置。

## 4. Gate B：外部 XLSX 导入与更新

只有 Gate A 通过后才向 Leader 分发标准模板和测试源文件。导入前记录客户、Lead、活动、任务和用户数量并执行完整备份。

1. Leader 登录 Export / Import，选择顶部 `Excel Import` 页签；JSON Exchange、Data Governance 和 Customer Merge 分别独立验证。
2. 在四步向导中创建完整备份、选择外部 `.xlsx`，再点击 Run Preflight。预检只解析和报告，不写入数据库。
3. 在固定高度复核窗口内展开成员映射、客户匹配和问题分组；不能确认的无效记录可明确排除。
4. 点击固定操作栏中的 Apply corrections & recheck，确认 `Ready to import` 后执行 Import & Merge。
5. 核对新建、更新、归档、跳过和质量提示数量。
6. 保持 `dataset_id` 和外部键不变，修改允许更新的字段后再次导入。
7. 第三次导入完全相同文件，确认记录数量不再增长。

Gate B 通过标准：预检零写入、提交原子化、旧哈希拒绝、重复导入幂等、缺失信息进入质量队列，且安装目录和程序文件未因导入而改变。

### 4.1 导入后的业务功能抽查

1. 在跟进管理分别核对计划日期页签与长期未跟进条件。前者使用下一次计划跟进日期，后者使用“最近正式跟进 → 询盘日期 → 创建日期”回退，不应得到相同口径。
2. 按负责人账号业务地区筛选。五类地区为 `GLOBAL / 欧洲 / 北美/加拿大/澳洲 / 俄罗斯/土耳其/中东 / 东南亚`；`GLOBAL` 不是清空条件。
3. 组合地区、负责人、技术人员、搜索和时间条件，确认结果取交集；清空地区时选择“全部地区”。
4. 核对地图的精确、近似、缺失数量。近似点不能当作准确地址；无网时应显示底图状态，但列表和坐标复核仍可使用。
5. 仅用不敏感测试地址验证单条与小规模批量搜索；确认界面显示实际服务商。地址字段可能发送给高德后再因可回退故障发送给 Nominatim，底图还会访问 CARTO/OpenStreetMap 瓦片。高德 Key 只在本机设置，不进入证据截图、日志、安装包或仓库。
6. Leader 用一组测试客户名称/别名验证模糊候选、分数、只读迁移预览与一次安全合并。不得只凭高分自动合并。

## 5. Gate C：账号映射与权限

账号必须在导入前由 Leader 创建。XLSX 中的姓名、缩写和大小写变体只能映射到现有账号，不能自动新建成员。

- Leader：可处理所有来源映射、客户匹配、导入和数据治理。
- Sales：只能成为 Lead owner 或协作成员，只能读取自己负责或协作的商业数据。
- Tech：只能成为售前/售后任务执行人，只读取自己的任务和必要关联数据，不返回报价、金额、PO、输单原因等字段。

分别用 Leader、目标 Sales、非目标 Sales、目标 Tech 和非目标 Tech 登录核对同一批导入数据。未知账号、停用账号、歧义映射、Tech 作为 Lead owner、Sales 作为技术任务执行人都必须阻断提交。

## 6. Gate D：终端文件分发与同步

本地分散式部署使用定向终端包同步，不使用 XLSX 作为持续同步协议。Sales JSON 与 Tech 任务包是两条独立链路，必须分别验收。

### 6.1 Sales JSON 同步

1. Sales 在终端 A 导出自己的数据包，记录导出时间、文件哈希和记录数。
2. Leader 向 Sales 分发时，在 JSON 数据交换页明确选择接收成员。新包只应包含该 Sales 作为负责人的 Lead；不要把 Leader 全量包改名后发送。
3. 目标 Sales 在终端 B 做导入预检，核对包内接收账号、权限允许范围、联系人关联和冲突信息；非目标成员导入同一包必须被拒绝。
4. 导入前保存完整备份和数据库快照，再执行合并。
5. 核对有主联系人的 Lead 仍指向正确联系人；没有邮箱但有姓名的多个联系人不得互相覆盖。
6. 在终端 B 新增一条本地活动，再次导入旧数据包，确认本地活动未丢失。
7. 重复导入同一数据包，确认客户、Lead、互动和任务不重复。
8. 由 Leader 重新导出已汇总数据时，只向有权限的成员分发相应文件。

Sales JSON 只包含附件元数据；附件文件、完整备份和授权文件使用独立渠道传递。不要把 `.jptauth` 混入业务同步文件夹。

### 6.2 Tech 任务包往返

1. Leader 创建完整备份，记录目标 Tech、售前/样品任务数和售后任务数。
2. Leader 进入“导出 / 导入 → Tech Task Packages”，选择启用中的目标 Tech，导出 `.jpttask`。该包是当前终端上该 Tech 当时全部未归档分配的完整快照，不是增量包；任一 Leader 后续签发的新快照都会替代此前其他 Leader 为同一 Tech 签发的旧快照。
3. Leader 通过可信内部渠道点对点发送；另通道告知文件名、任务数和导出时间。
4. 目标 Tech 在独立“技术任务包”页签选择 `.jpttask`，先预检来源、精确接收人、任务数、错误、冲突和撤回警告；非目标 Tech 预检/导入必须被拒绝。新快照中缺失的旧任务代表 Leader 撤回分配，导入后 Tech 本地对应任务归档。
5. 无错误且无冲突后导入，在“售前 / 样品”与“售后”核对卡片数、询盘编号、客户上下文和请求内容。
6. Tech 只更新本人允许的状态与结果字段，保存后重新打开卡片核对。
7. Tech 回到任务包页签导出 `.jptresult`，用可信渠道回传给原 Leader。
8. Leader 在“导入技术处理结果”选择 `.jptresult`，预检来源 Tech、Leader 接收账号、任务归属、是否改派/归档和基础快照。三方比较只在 Leader 与 Tech 修改同一结果字段且值不同时阻断；不同字段可合并保留。
9. 仅在整包无错误、无冲突时合并。在 Leader 原任务卡片核对状态和结果，然后向 Tech 回执。
10. 再次导入同一包，确认返回重复/幂等结果，不新增副本或重复改写。

Tech 任务包的正常内容只包含被分配任务、执行必需的最小客户/需求上下文，以及 Tech 允许回传的状态与结果。包内不应出现报价、金额、PO、输单原因、联系人、附件文件或完整备份。

冲突处理：

- 接收人/组织不符或内容校验失败：隔离文件，不通过改名绕过，由 Leader 核对渠道后重新导出。
- 完整快照撤回：新快照不含旧任务时，如 Tech 无未导出更改，或结果已导出且导出后未再修改，可带警告导入并归档本地任务。
- Tech 本地有未导出结果：如从未导出，或导出 `.jptresult` 后又修改，撤回/刷新必须阻断；先重新导出并让 Leader 合并，再导入新 `.jpttask`。
- 任务已改派、归档或缺失：不强制合并旧结果；Leader 核对归属后重新分发。
- 同字段冲突：Leader 和 Tech 在原快照后修改同一结果字段且值不同时阻断；不同字段可安全合并，不静默覆盖。
- 旧完整快照：快照生成时间不新于上次已导入快照，或单任务基线倒退时拒绝导入，由 Leader 重新导出。
- 旧数据库副本：仅当任务、Lead、客户、负责人、版本及允许同步内容与包基线完全一致时，系统才会带警告复用原记录且不重复新增；任何陈旧、部分存在或内容不一致均阻断，不做猜测性覆盖。
- 任一任务有错误或冲突：整包不应部分静默写入，保留预检证据并先解决所有阻断。

任务包用带时区的生成时间阻止旧包倒灌。参与测试的 Windows 与 macOS 电脑必须开启系统自动日期、时间及时区同步。

## 7. 恢复与回滚

- 业务操作失败：保留原文件和日志，使用导入前备份恢复，不手工拼接 SQLite 文件。
- 程序升级失败：退出程序，安装上一版；若 schema 已升级且数据异常，恢复升级前完整备份。
- 成员换机：新电脑生成 `.jptreq`，Leader 重签；旧授权记录转为历史。
- 设备丢失：Leader 停用成员或重签新设备；当前离线版不承诺即时远程撤销旧设备。

## 8. 反馈要求

每个问题必须包含：Gate、测试编号、平台与版本、角色、设备架构、复现步骤、预期结果、实际结果、截图或日志路径、数据是否可恢复、P0/P1/P2、是否阻塞下一 Gate。

- P0：数据丢失、数据错误、权限泄露或授权绕过。
- P1：核心安装、登录、导入或同步链路阻塞。
- P2：低频问题且存在明确绕行方式。

## 9. 0.11.8 业务口径速查

| 功能 | 判定口径 | 容易误解的点 |
|---|---|---|
| 全部地区 | 不限制负责人业务地区 | 与 `GLOBAL` 不同 |
| GLOBAL | 负责人账号的真实全球业务归属 | 不是清空筛选 |
| 已逾期/今日到期/未来 7 天 | 下一次计划跟进日期 | 无计划日期不会被自动算入 |
| 长期未跟进 | 最近正式跟进，缺失则询盘日期，再缺失则创建日期 | 与计划到期是两套独立条件 |
| 客户模糊候选 | 主名称和别名相似度 | 分数只帮助人工判断，不自动合并 |
| 地图近似点 | 区域级参考位置 | 不能替代精确地址 |
| 卡片排序 | 各页面按阶段、计划日、业务日期稳定排序 | 不是客户名称排序，也不依赖数据库偶然顺序 |
| Leader → Sales JSON | 先选接收成员，只导出该成员负责的 Lead | 非目标成员导入会被拒绝 |
| Leader → Tech `.jpttask` | 只分发该 Tech 当前任务及最小上下文 | 非目标 Tech 被拒绝，不含金额/联系人/附件 |
| Tech → Leader `.jptresult` | 只回传 Tech 允许的状态和结果字段 | 改派、归档、版本冲突被阻断；重复包幂等 |
