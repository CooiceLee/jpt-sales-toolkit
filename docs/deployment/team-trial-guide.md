# JPT Sales Toolkit 团队试装与独立模块验收手册

适用版本：`0.11.0-internal`。产品只维护 Windows 10/11 x64、macOS Apple Silicon arm64 和 macOS Intel x86_64。

## 1. 验收原则

团队试运行分为四个独立模块：程序安装、外部 XLSX 导入、账号权限映射、终端数据包同步。每个模块使用独立输入、独立证据和独立结论。安装包不得预装业务 Excel、成员授权、业务数据库或测试业务数据。

推荐测试顺序：

1. Gate A：纯净安装、激活、基础操作和本地数据持久化。
2. Gate B：在 Gate A 通过后的程序中单独导入和更新 XLSX。
3. Gate C：使用真实测试账号核对导入后的权限划分。
4. Gate D：在两个独立终端数据目录之间验证 JSON 数据包同步。

任何 Gate 出现 P0 或 P1 问题时停止进入下一 Gate，先保留日志、截图和测试前备份。

## 2. 分发文件边界

公开给所有测试成员的文件只有其电脑架构对应的安装包、成员安装指南和 SHA-256 校验文件。Leader 单独保管标准 XLSX、测试源文件、账号清单、签发器口令、`.jptauth`、完整备份和同步数据包。

- 安装包：统一程序，不区分 Leader / Sales / Tech。
- `.jptreq`：成员设备请求，可发送给 Leader。
- `.jptauth`：Leader 针对成员和设备签发，必须点对点发送。
- XLSX：外部数据摄取文件，只由 Leader 预检和提交。
- JSON：成员终端之间的数据交换包，不等同于完整备份。
- 备份 ZIP：包含数据库、附件和授权配置，按敏感文件管理。

## 3. Gate A：纯净安装与基础程序

### 3.1 安装前

1. 根据设备选择 Windows x64、macOS arm64 或 macOS x86_64 安装包。
2. 使用 `SHA256SUMS.txt` 核对安装包哈希。
3. 确认测试电脑没有复制旧版 `data` 目录；升级测试除外。
4. 确认没有把 XLSX、`.jptauth` 或业务数据库放入安装目录。

### 3.2 Windows

运行 Setup EXE。若 SmartScreen 提示未知发布者，只在文件名和 SHA-256 均与 Leader 提供记录一致时选择“更多信息 → 仍要运行”。默认安装到当前用户目录，不要求管理员权限。

### 3.3 macOS

打开对应架构的 DMG，把 JPT Sales Toolkit 拖入 Applications。当前内部包未做 Apple notarization；若 Gatekeeper 阻止首次打开，在 Finder 中按住 Control 点击应用并选择“打开”，再次确认。不要使用来源不明的终端命令绕过系统安全策略。

### 3.4 首次激活

- 首位 Leader 选择 `Set up a new team`，设置登录密码和至少 12 位签发器口令，随后立即生成完整备份。
- 已有成员选择 `Join an Existing Team`，下载 `.jptreq`，发送给 Leader。
- Leader 签发 `.jptauth`，授权文件和 16 位验证码必须通过两条不同可信渠道发送。
- 成员导入 `.jptauth`、输入验证码、设置本地密码并登录。

### 3.5 Gate A 通过标准

- `/api/health` 显示正确版本并只监听 `127.0.0.1`。
- Leader、Sales、Tech 均可按授权登录。
- 新建一条带唯一测试标识的客户或 Lead，退出程序并重启后仍存在。
- `Exit JPT` 能停止后台程序，覆盖升级不丢数据。
- 卸载不删除用户数据目录；完整备份能够恢复数据库、附件和授权配置。

## 4. Gate B：外部 XLSX 导入与更新

只有 Gate A 通过后才向 Leader 分发标准模板和测试源文件。导入前记录客户、Lead、活动、任务和用户数量并执行完整备份。

1. Leader 登录 Export / Import，选择外部 `.xlsx`。
2. 点击 Preflight Check。预检只解析和报告，不写入数据库。
3. 处理成员映射、客户匹配和阻断项；不能确认的无效记录可明确排除。
4. 再次预检，确认 `Ready to import` 后执行 Import & Merge。
5. 核对新建、更新、归档、跳过和质量提示数量。
6. 保持 `dataset_id` 和外部键不变，修改允许更新的字段后再次导入。
7. 第三次导入完全相同文件，确认记录数量不再增长。

Gate B 通过标准：预检零写入、提交原子化、旧哈希拒绝、重复导入幂等、缺失信息进入质量队列，且安装目录和程序文件未因导入而改变。

## 5. Gate C：账号映射与权限

账号必须在导入前由 Leader 创建。XLSX 中的姓名、缩写和大小写变体只能映射到现有账号，不能自动新建成员。

- Leader：可处理所有来源映射、客户匹配、导入和数据治理。
- Sales：只能成为 Lead owner 或协作成员，只能读取自己负责或协作的商业数据。
- Tech：只能成为售前/售后任务执行人，只读取自己的任务和必要关联数据，不返回报价、金额、PO、输单原因等字段。

分别用 Leader、目标 Sales、非目标 Sales、目标 Tech 和非目标 Tech 登录核对同一批导入数据。未知账号、停用账号、歧义映射、Tech 作为 Lead owner、Sales 作为技术任务执行人都必须阻断提交。

## 6. Gate D：终端文件分发与同步

本地分散式部署使用 JSON 数据包同步，不使用 XLSX 作为持续同步协议。

1. Sales 在终端 A 导出自己的数据包，记录导出时间、文件哈希和记录数。
2. Leader 在终端 B 做导入预检，核对权限允许范围和冲突信息。
3. 导入前保存完整备份和数据库快照，再执行合并。
4. 在终端 B 新增一条本地活动，再次导入旧数据包，确认本地活动未丢失。
5. 重复导入同一数据包，确认客户、Lead、互动和任务不重复。
6. 由 Leader 重新导出已汇总数据时，只向有权限的成员分发相应文件。

JSON 只包含附件元数据；附件文件、完整备份和授权文件使用独立渠道传递。不要把 `.jptauth` 混入业务同步文件夹。

## 7. 恢复与回滚

- 业务操作失败：保留原文件和日志，使用导入前备份恢复，不手工拼接 SQLite 文件。
- 程序升级失败：退出程序，安装上一版；若 schema 已升级且数据异常，恢复升级前完整备份。
- 成员换机：新电脑生成 `.jptreq`，Leader 重签；旧授权记录转为历史。
- 设备丢失：Leader 停用成员或重签新设备；当前离线版不承诺即时远程撤销旧设备。

## 8. 反馈要求

每个问题必须包含：Gate、测试编号、平台与版本、角色、设备架构、复现步骤、预期结果、实际结果、截图或日志路径、数据是否可恢复、P0/P1/P2、是否阻塞下一 Gate。

- P0：数据丢失、数据错误、权限泄露或授权绕过。
- P1：核心安装、登录、导入或同步链路阻塞。
- P2：低频问题且存在明确绕行方式。
