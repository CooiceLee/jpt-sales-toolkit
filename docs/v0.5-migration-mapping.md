# JPT Sales Toolkit v0.5 Migration Mapping

This document defines how legacy JSON-based `Inquiry` records migrate into the new SQLite model.

## 1. Migration Pipeline

Order of execution:

1. `migrate_users.py`
2. `migrate_customers.py`
3. `migrate_leads.py`
4. `migrate_activities.py`
5. `migrate_tasks.py`
6. optional `migrate_artifact_links.py`
7. generate `migration_report.json` and `legacy_maps.json`

Output files:

- `migration_report.json`
- `legacy_id_map.json`
- `legacy_user_map.json`
- `new_database.sqlite`

## 2. Legacy User Mapping

Legacy source:

- `config/user.json`
- `config/team.json`
- fallback values from `created_by`, `assigned_sales`, `pre_sales_owner`, `technician`

Rule:

1. Build a set of unique legacy user IDs from config and data.
2. Create new `users` records with generated UUIDs.
3. Generate an initial plain password as `{legacy_user_id}JPT2026`.
4. Store only its password hash in `users.password_hash`.
5. Create a `legacy_user_id -> new_user_uuid` map.
6. Replace all legacy string user IDs during migration.

Recommended file:

```json
{
  "Li": {
    "user_id": "uuid-user-li",
    "initial_password": "LiJPT2026"
  },
  "Ayden": {
    "user_id": "uuid-user-ayden",
    "initial_password": "AydenJPT2026"
  }
}
```

MVP note:

- migrated users are not forced to reset password in schema v0.5
- if needed later, first-login password rotation can be added at the auth layer

## 3. Customer Creation Rules

Legacy `Inquiry` becomes a `Customer` candidate based on:

- `company_name`
- `email` domain
- `website`
- `country/city/address`

Matching order:

1. exact `customer_contacts.email`
2. exact `customer_domains.domain`
3. exact `customers.normalized_name`
4. alias/domain candidate review
5. create new customer

One customer may own multiple migrated leads.

## 4. Lead Creation Rules

Each legacy `Inquiry` becomes one `Lead`.

- `legacy_inquiry_id` preserves the original ID
- `display_id` is regenerated with the new sequence rule
- `owner_id` is resolved from `assigned_sales`
- `customer_id` comes from the customer matching phase
- search views should support lookup by both `display_id` and `legacy_inquiry_id`

## 6. Stage Mapping

| Legacy stage | New sales_stage | New fulfillment_status | New service_status |
|---|---|---|---|
| `Inquiry` | `New` | `Not Started` | `None` |
| `Following` | `Following` | `Not Started` | `None` |
| `Sampling` | `Following` | `Not Started` | `None` |
| `Quoting` | `Quoted` | `Not Started` | `None` |
| `Closed Won` | `Won` | `Not Started` | `None` |
| `Fulfillment` | `Won` | `In Progress` | `None` |
| `After-sales` | `Won` | `Completed` or `In Progress` | `Open` |
| `Closed Lost` | `Lost` | `Not Started` | `None` |

Additional rule:

- If `production_status` exists, it overrides fulfillment inference.
- If `after_sales[]` contains records, set `service_status` to `Open` unless the migrated task status implies `Resolved` or `Closed`.

- `sample_confirmed_date`

Mapping:

| Legacy field | New destination |
|---|---|

| `sample_result` | `result_json.result` |

## 10. Archived and Invalid Data Handling

Rules for invalid legacy values:

- invalid numeric `lat/lng` -> set null and note in `migration_report.json`
- invalid dates -> preserve raw value in `extra_json` and note warning
- empty strings -> normalize to null
- unknown user IDs -> create placeholder inactive users and warn

Example warning:

```json
{
  "legacy_inquiry_id": "INQ-202604-BC90",
  "field": "expected_delivery",
  "warning": "invalid_date_preserved_in_extra_json",
  "raw_value": "23饶"
}
```

## 10.1 Legacy Artifact Handling

The legacy system does not have a reliable standalone attachment store in the current sample data.

Migration rule:

- no mandatory file-copy attachment migration is required in MVP
- URL-like fields such as `sample_report_link` remain in task JSON unless a real local file exists
- if a real local file path is discovered later, an attachment metadata row may be generated
- `migrate_artifact_links.py` is therefore optional and may be a no-op in early migrations

## 11. Rollback

Rollback strategy:

1. Backup legacy `data/` to `data/backups/legacy_{timestamp}.zip`
2. Run migration into a brand-new SQLite file
3. Validate row counts and report
4. Only switch runtime config after successful validation
5. On failure, discard new SQLite file and keep legacy data untouched
