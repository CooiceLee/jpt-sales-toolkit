## 本版交付的能力

### 一种规划方式

行程只有一种规划方式：团队出行。一个人出差就是一人成队，计划新建时就带上创建者；页面上不再有"规划模式"选择器，也不再有独立的"中国出发时间窗 / 返回中国时间窗"——行程自己的起止日期就是唯一的时间窗。

这次统一暴露出团队引擎与旧算法之间的差距，本版逐条补齐：

| 能力 | 统一前的表现 | 现在 |
|---|---|---|
| 手工拖动顺序 | 团队引擎不读 `stop_order`，拖动无效 | 按拖动后的顺序走 |
| 自动顺序 | 团队引擎按录入顺序走，不看地图 | 与旧算法同一套地理排序，机场/中转点仍跟随它服务的拜访 |
| 周末与节假日 | 客户拜访会被排到周六 | 拜访只排在工作日；出差、住宿、机场等待照常按日历 |
| 上午/下午偏好 | 完全忽略 | 未约定时间的拜访按偏好选半天 |
| 拜访时长与锁定 | 生成后不落库，保存完就丢 | 时长、停留天数、时段偏好、锁定状态随路线一起保存 |
| 已确认时间被算法移动 | 仍显示"已确认" | 改为"需重新确认" |
| 停靠编号 | 保持录入顺序，编号与路线不符 | 按实际到访先后重新编号 |
| 失效的交通选择 | 静默丢弃 | 手工顺序下拒绝并说明，自动顺序下在摘要里报告 |
| 约定时间落在周末 / 与偏好冲突 | 团队引擎不报 | 作为风险显示在风险条里 |
| 路线排到行程开始日之前 | 摘要仍称"在时间窗内" | 明确写出早于计划开始日多少天 |

旧的单人路线算法（`_calculate_trip_itinerary`）连同它专用的 7 个辅助函数已删除：它已经不在任何运行路径上，留着只会让测试验证一条用户永远走不到的代码。原先经由它验证的机场展开、周六出发、约定时间优先三项，改为经真实路径验证。

### 团队出差规划

一次行程可以由多人分头完成：分开出发、中途会合、各自返回。行程、地图、导出与拜访卡片都按人区分，同一段共同行程只显示一行。

### 出差文件分成两份

| 文件 | 内容 | 用途 |
|---|---|---|
| 共享行程 | 出行人、日期、地点、详细地址、交通安排 | 供本次出行相关人员确认 |
| 行程 + 拜访准备 | 上述内容，另加拜访目的、备注、客户人员、渠道代理陪同、JPT 参会人员、设备与议题 | 只发给实际前往的人 |

日历（ICS）走共享口径——它会被单独转发。八个下载各自命名，形如 `Trip-Sept-shared-20260902.xlsx`。

### 现场执行工作簿与结果回流

拜访带着一份工作簿到现场填写，填完回传录入。准备区只读，只有 12 个执行结果字段可填。样品与报价可以**不作答**（存为空，而不是"否"），标记为已拜访或需要跟进则必须写明实际发生的日期与上午/下午。

回传的工作簿不能自证身份：任何人都能取消隐藏工作表的保护并改写它。因此**签发方保留清单**——哪一行对应哪个拜访、导出时各字段是什么值都存在本机数据库，文件只带自己的编号和每行一个 token。录入前先展示会改动什么，逐个冲突按所选一边判定，选中的行在同一事务里全部写入或全部不写。

## 已知限制

1. **现场执行工作簿只能在签发它的那台机器上录入。** 清单存在签发方数据库里，换一台机器打开会得到"这份工作簿不是本机签发的"。这是刻意的：文件自证身份就意味着可以被改写。
2. **工作簿内的日期校验只保证是合法日期**，不校验是否落在行程窗口内；真正的业务规则在服务端。
3. **Markdown 与 CSV 只有一个版本**，始终含拜访准备内容，界面已标为"数据格式，含拜访准备"。
4. **约定时间可以排在行程开始日之前。** 客户约定的时间是事实，行程日期被改到它之后时，路线仍围绕约定时间安排，因而会跑在计划开始日之前。这种情况会同时报出"赶不上约定拜访"和"早于计划开始日 N 天"两条提示，由使用者决定改哪一边。
5. **旧计划里原本就没有出行人的，升级后一律记为计划所有者一人。** 真实名单无从得知，只能由使用者在"出行团队"里补。
6. 地图底图标注语言仍无法统一为中文（瓦片为图片，属外部依赖）。

## 放行规则

1. 数据丢失、错误迁移、权限扩大、错误任务归属或行程导出错客户属于 P0，立即停止发布。
2. 安装、启动、登录、保存、升级、恢复或正式行程下载阻塞属于 P1，Release 保持 Pre-release 且不扩大分发。
3. 双平台 CI 与资产校验全部有证据后，才能创建 Pre-release 供扩大测试。
4. 真实 Windows 与 Apple Silicon 团队设备完成新装、覆盖升级、重启、数据保留与实测前，不得讨论 Stable / Latest。
