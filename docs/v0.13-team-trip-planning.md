# v0.13 设计：团队出差规划（Appointment-driven Team Trip Planning）

状态：设计已定稿，待实现。分支 `feature/anchor-planning`，暂不合并 `main`。

## 为什么要改

现在的 Trip Planner 以「路线顺序」为中心：用户排 `stop_order`，系统沿一个游标推进，算出时间。

真实的销售出差不是这样。真实输入是：

> 团队要拜访这几个客户；其中几个已经和客户约好了时间；我们有几个人可以分头去。
> 请先告诉我这个商务行程成不成立，然后我们再各自安排交通。

两处根本不匹配：

1. **约定时间是既成事实，不是排序的结果。** 现在只能先排顺序、再被动校验预约，赶不上就报错。
2. **单游标 = 假设整趟只有一个人。** 实测：两个客户约在同一时段不同城市，会被硬性拒绝
   （`ValueError: The route cannot reach this visit before its locked time`），
   而现实中由两位同事分头拜访完全合法。

所以 v0.13 把中心从「路线顺序」换成「谁、在什么时候、必须出现在哪个客户现场」。路线是这些事实算出来的结果。

## 不可违背的约束（Invariants）

**I1 — Trip Team 是特性开关，也是灰度边界。**
计划新增 `planning_mode`（`legacy` / `team`）。`legacy` 计划走**现有单游标引擎与现有界面，行为一字不变**。
只有用户为某个计划显式建立 Travel Team 后才进入 `team`。存量计划零风险，团队可逐个计划切换，出问题可退回。
本轮已发生过三次「实现→实测证伪→回滚」，这个开关是这次大改能否安全落地的分水岭。

**I2 — 已约定的时间压过系统偏好。**
`avoid_weekends` 与 `holiday_dates` 只约束**系统自动安排**的 Flexible 拜访。
Fixed 预约无条件按约定时间落位。
实测当前为硬 bug：客户约在周六、或约在中国节假日（客户在德国），都会被
`A locked stop cannot use a skipped day` 拒绝。
`holiday_dates` 语义收窄为「自动排 Flexible 时应避开的日期」，不再解释为「全球客户都不能拜访」。

**I3 — 不知道路线时不编造路线。**
不生成现实中不存在的行程段。两人分头时不产生「客户A → 客户B」这种段，
汇合点未确定前该区间的里程与耗时**不计算**，而不是给一个错数字。
里程/耗时按成员统计；`team total` 第一版不显示（人-公里口径取决于将来算车辆成本还是人员旅行量，现在定死是过早决策）。

**I4 — 只有结构性数据错误才阻断保存。**
缺坐标、非法日期、不存在的用户 → 阻断。
「看起来赶不上」「有人时间重叠」「返程超出计划结束日」→ **风险提示，Preview / Save / Export 全部照常**。
这是行程规划工具，不是审批系统。

**I5 — 只增加真实业务需要的复杂度。**
不做：VRP solver、员工自动分配、workforce optimizer、显式 split/merge 指令、
全球节假日日历、路线图编辑器、实时航班、费用优化。

## 模型

三个对象就够：

```
Member   —  谁出差（可选覆盖各自的出发/返回地）
Event    —  一次活动：地点 + 时间 + 时长 + 参与人 + 类型（客户拜访 / 酒店 / 机场 / 中转 / 休息）
Leg      —  某一位成员从上一个活动到下一个活动的移动
```

调度从单游标改为**每人一个游标**：

```
member_state[user_id] = { time, location }

按时间推进 Event：
  for member in event.participants:
      leg = 计算(member.location → event.location)
      到达 = member.time + leg.duration
      若 到达 > event.start:  记录风险（不阻断）
      member.location = event.location
      member.time     = event.end
```

**Split 与 Merge 不需要建模，也不需要按钮。** 它们是事件参与人差异的自然结果：
下一个活动参与人不同 → 自动分头；同一个活动有多人参与 → 自动汇合。

## Schema 变更

本版接受 schema 升级——单游标数据模型已被证明无法正确描述团队出差。但保持最小。

**新表 `trip_plan_members`**
```
id, plan_id, user_id
origin_name_override / origin_lat_override / origin_lng_override
destination_name_override / destination_lat_override / destination_lng_override
created_at, updated_at
UNIQUE (plan_id, user_id)
```
一张表解决三件事：谁参加、谁需要独立游标、谁从不同城市出发或返回。
覆盖字段可选，默认继承计划级出发/返回地，绝大多数用户看不到它们。

**`trip_plans` 增列** `planning_mode TEXT NOT NULL DEFAULT 'legacy'`（见 I1）。

**`trip_plan_legs` 增列** `member_id TEXT REFERENCES users(id)`，可为 NULL。

`member_id` 存的是 **`users.id`，不是 `trip_plan_members.id`**：一条 Leg 记录的是"谁走了这段"，
这个事实必须在团队名单被编辑之后仍然可读。成员是否属于本次 Trip Team 由服务层校验
（本项目 `PRAGMA foreign_keys = 0`，FK 是声明性文档，不能依赖它兜底）。

唯一约束用**两个 partial index**，而不是一个合并索引：
```
(plan_id, leg_key)             WHERE archived_at IS NULL AND member_id IS NULL      -- legacy
(plan_id, member_id, leg_key)  WHERE archived_at IS NULL AND member_id IS NOT NULL  -- team
```
SQLite 在唯一索引中把 NULL 视为互不相同，单个合并索引会静默失去对 legacy 计划重复 Leg 的保护。
已实测三种行为：legacy 重复被拒、不同成员可共用同一 `leg_key`、同一成员重复被拒。

理由（已在代码中核实）：现有唯一索引是 `(plan_id, leg_key)`，而 `leg_key` 仅由相邻节点生成。
两位成员走同一对起终点但交通方式不同——张三自驾、李四坐火车从法兰克福到斯图加特——
就需要两条 Leg、`leg_key` 相同，**直接违反唯一索引**。这不是可以合并的重复数据，
而是两个独立的旅行事实，必须各存一条。显示层负责在
`from / to / 时间 / 方式` 全部相同时视觉合并为「张三 · 李四 — 火车 FRA → 斯图加特」。

**`trip_plan_free_stops` 增列** `participant_user_ids_json TEXT`。
`NULL` = 全体成员（普通行程什么都不存），`["user-z"]` = 仅张三。
客户拜访复用现有 `trip_visit_briefings.participants_json`，自由停靠点是唯一的缺口。
两者形状不同是有意的：拜访需要职责与备注，酒店只需要知道是谁住。
不加此列，Batch 2 做「张三住法兰克福、李四住巴黎」时必然要再升一次 schema。

**同时必须修的隐患**：`saved_airports()` 与 `locked_overrides()` 目前都以 `leg_key` 作为
Python 字典键，两位成员共用同一 `from→to` 时，机场设置与交通 override 会互相覆盖。
仅改数据库索引不够，查找键必须一并改为 `(member_id, leg_key)`。

**`stop_order` 在 team 模式淡出**，不复用为「成员 lane 内顺序」。
team 模式的顺序由 `planned time + participants + member-local sequence` 决定。
同一个 API 字段在两种模式下表达不同含义会留下长期契约歧义。
`legacy` 模式继续原样使用 `stop_order`。

## 界面

三个区域是**同一份规划状态的不同视图**，不是三个各自保存状态的子系统：

```
Trip Header        日期 · Travel Team · 默认出发/返回地
Commitments        客户、固定/浮动预约、参加人员、停留时长   ← 约束输入
Team Timeline      规划主体；同行合并显示，分头才展开 lane
Map / Inspector    当前活动或行程段的地图与交通编辑
Unscheduled        尚未安排的 Flexible 客户与停靠点（抽屉）
```

- **Timeline 成为主体，客户列表成为输入池**（原来是 Stop 列表为主体、Timeline 为结果）
- **同行时不展开 lane**，界面复杂度与现在一致；只有真正分头才展开，汇合后自动合并
- **上下移动降级**为「同一成员、同一浮动窗口内的局部人工调整」，不再是规划核心
- 客户卡片直接暴露参加人员，不必进入「拜访准备」两层子面板
- 自由停靠点（酒店/机场/中转/休息）沿用同一套参与人语义：默认「全体成员」，分头时才选择特定成员

**Generate Initial Plan** 先只产出商务骨架（钉住 Fixed、建议 Flexible、分配到成员），
再在空档生成交通占位与建议方式，由用户确认。先排必须做什么，再安排怎么过去。

## 风险提示（统一收口，全部不阻断）

顶部只显示「计划状态 · N 项风险」，展开后为业务语言，不出现实现术语：

- **人员时间重叠**：张三在 9 月 16 日上午同时安排了两场客户拜访。请调整参加人员，或确认由其他成员负责其中一场。
- **并行拜访未指派**：9 月 16 日上午有 2 场同时进行的客户拜访，其中巴黎客户尚未指定拜访人员。
- **交通赶不上预约**：按当前交通安排，李四预计无法在 9 月 17 日上午前到达慕尼黑客户。请调整交通方式、出发时间或拜访人员。
- **周末固定预约**：该客户拜访已约在 9 月 19 日（周六），系统将保留该预约时间。
- **汇合点未确定**：9 月 16 日上午之后团队分头行动，下一段共同路线的起点尚未确定。在添加共同酒店、机场或其他停靠点之前，这一段的交通距离与时间不会计算。
- **成员返程超期**：李四按当前安排预计在计划结束时间之后返回，请确认返程时间或调整行程。

## 汇总

计划级只保留无歧义的：成员数、客户拜访数、固定预约数、并行区间数、风险数。
里程与耗时**按成员**给出（各自的距离、交通时长、预计结束时间、风险数）。

## 开发批次

每批独立可验收。

**Batch 1 — 团队调度基础**
`trip_plan_members`、`planning_mode`、member-aware Leg 身份（含字典键修正）、
Fixed 预约压过周末/节假日、每人一个游标、并行识别、风险生成、按成员生成 Leg。
验收：场景 A / C / D / F / G / J

**Batch 2 — 分头与汇合**
自由停靠点参与人范围、共同活动导致的游标汇合、多次分叉汇合。
验收：场景 H / I

**Batch 3 — 预约感知建议**
Fixed 分组、Flexible 贪心插入（仅在已指派成员的 lane 内、且不跨并行边界）、
建议预览与「应用建议」。永不静默重排。
验收：场景 B

**Batch 4 — Timeline / Map / 导出**
lane 展开与合并、Map 随选择联动、XLSX / HTML / ICS 与计算结果同源。
验收：全部场景的导出一致性

## 验收场景

均以真实海外出差为原型，不用纯测试数据。

- **A 单人普通行程**：上海 → 法兰克福 → 巴黎 → 上海。多人能力不得导致原功能回归。
- **B Fixed + Flexible**：法兰克福 9/15 PM 固定、斯图加特浮动、巴黎 9/18 AM 固定 → 能建议斯图加特的合理位置。
- **C 合法并行**：9/16 AM 法兰克福（张三）+ 巴黎（李四）→ 可保存，且**不产生**法兰克福 → 巴黎行程段。
- **D 人员冲突**：同上但两场都指派张三 → 提示风险，仍可保存。
- **E 并行后汇合**：法兰克福 ┐ 巴黎 ┘ → 斯图加特酒店 → 慕尼黑。酒店之后恢复共同路线。
- **F 未汇合**：分头后没有共同停靠点 → 后续共同区间明确「不计算」，计划仍可保存与导出。
- **G 起点直接分叉**：上海 →（张三 法兰克福 / 李四 巴黎）两条真实行程段，互不虚连。
- **H 分开出发后汇合**：不同成员从不同中国城市出发，海外汇合。
- **I 多次分叉汇合**：同行 → 分开 → 汇合 → 再分开 → 汇合 → 返程，成员游标始终正确。
- **J 周末固定预约**：即使开启跳过周末，仍按周六安排并提示，不拒绝。

## 已知会失效、需要重写的既有契约

- `stop_order` 相关：5 个测试文件（`legacy` 模式的用例**原样保留**，作为特性开关未破坏旧行为的证据；team 模式新增独立契约）
- 上下移动相关：2 个前端契约测试
- 汇总字段与三种导出格式：改为 per-member

## 本版不做

VRP solver、员工自动分配、workforce optimizer、显式 split/merge 指令、
全球节假日日历、自动寻找汇合城市、个人酒店自动安排、实时航班、费用优化、
`team total` 里程数字。

## 工程性质

**调度核心重构，不是整个 Trip Planner 重写。**
被替换的是编排循环（谁的游标往哪里推进）；以下已验证的底层组件继续复用：
距离计算、交通方式选择、`build_leg()`、航班展开与机场处理、
日历/工作日槽位推进、地点解析、固定预约日期解析、交通 override、地理编码。
