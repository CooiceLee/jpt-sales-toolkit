# JPT Sales Toolkit v0.5 Page and API Matrix

This document maps pages to APIs and defines the MVP page boundaries.

## 1. Page Boundary Decisions

- `Follow-up Board`: separate page, implemented as a specialized lead view focused on next action and overdue status.
- `Deal Board`: separate page, implemented as a specialized lead view focused on quote, amount, win/loss, and cycle.
- `Technical Service`: separate page aggregating `pre_sales_tasks` and `after_sales_tasks`; each lead also exposes these as tabs in `Lead Workspace`.
- `Admin & Backup`: MVP page exists and covers backup, restore, legacy migration, and account list. Full user admin can remain limited in MVP.

## 2. Auth and Session

- Auth mechanism: JWT bearer token
- Token lifetime: 7 days
- Frontend stores token in local storage
- Request header: `Authorization: Bearer <token>`
- Login page also shows recent local accounts for quick switch

## 4. Combined Intake Endpoint

`POST /intake/submit`

Purpose:

- keep the intake UX to one submission
- guarantee atomic creation of customer, lead, owner assignment, and first activity

Request example:

```json
{
  "is_new_customer": false,
  "customer_id": "existing-customer-uuid",
  "customer": null,
  "lead": {
    "title": "200W MOPA quote request",
    "source_channel": "Email",
    "original_email": "raw email body...",
    "inquiry_date": "2026-04-27",
    "product_category": "MOPA Fiber Laser",
    "application": "Deep Engraving",
    "quality_grade": "B"
  },
  "owner_id": "user-uuid-1",
  "collaborator_ids": ["user-uuid-2"],
  "watcher_ids": ["user-uuid-3"]
}
```

Response example:

```json
{
  "customer_id": "customer-uuid-1",
  "lead_id": "lead-uuid-1",
  "display_id": "JPT-2604-0001"
}
```

MVP boundary:

- collaborator is supported in the MVP data model and permission model
- intake only requires `owner_id`
- `collaborator_ids` and `watcher_ids` are optional at intake time and may also be added later in `Lead Workspace`

## 7. Permission Matrix

Legend:

- `all`: can access all records
- `related`: only leads/customers connected to assignment or task
- `own-task`: only own technical tasks

| API | leader | owner | collaborator | watcher | tech |
|---|---|---|---|---|---|
| `GET /leads` | all | related | related | related | related |
| `GET /leads/{id}` | yes | yes | yes | yes | related |
| `PATCH /leads/{id}` | yes | yes | limited | no | no |
| `POST /leads/{id}/assignments` | yes | no | no | no | no |
| `GET /leads/{id}/activities` | yes | yes | yes | yes | related |
| `POST /leads/{id}/activities` (`comment`) | yes | yes | yes | yes | yes |
| `POST /leads/{id}/activities` (`follow_up`) | yes | yes | yes | no | no |
| `PATCH /customers/{id}` | yes | yes | limited | no | no |
| `POST /customers/{id}/archive` | yes | no | no | no | no |
| `POST /leads/{id}/archive` | yes | no | no | no | no |
| `POST /leads/{id}/pre-sales-tasks` | yes | yes | yes | no | yes |
| `PATCH /pre-sales-tasks/{id}` | yes | yes | yes | no | own-task |
| `POST /leads/{id}/after-sales-tasks` | yes | yes | yes | no | yes |
| `PATCH /after-sales-tasks/{id}` | yes | yes | yes | no | own-task |

`limited` means:

- collaborator can edit non-ownership business fields
- collaborator cannot archive, reassign owner, or alter restricted audit-sensitive fields

Collaborator allowed lead fields in MVP:

- `title`
- `product_category`
- `product_series`
- `power_range`
- `wavelength`
- `application`
- `material`
- `quality_grade`
- `urgency`
- `estimated_value`
- `next_followup_date`
- `quotation_id`
- `quotation_date`
- free-text business notes inside `extra_json`

Collaborator restricted lead fields in MVP:

- `owner_id`
- `archived_at`
- `row_version`
- `sales_stage` transitions into `Won` or `Lost`
- `fulfillment_status`
- `service_status`
- `deal_amount`
- `po_number`
- `currency`

## 8. Conflict Response Contract

When `row_version` mismatches:

Status:

- `409 Conflict`

Response body:

```json
{
  "error": "conflict",
  "current_version": 5,
  "your_version": 4,
  "current_data": {
    "id": "lead-uuid-1",
    "updated_at": "2026-04-27T10:20:00"
  },
  "message": "此记录已被他人修改，请刷新后重试"
}
```

Frontend behavior:

1. show blocking warning
2. offer `Refresh`
3. reload latest record
4. let user re-apply changes manually
