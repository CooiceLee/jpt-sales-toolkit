# JPT Sales Toolkit v0.6 试运行前端核对清单

## 使用方式

这份文档用于记录试运行中发现的前端显示、交互、字段映射和业务流程不匹配问题。每发现一个问题，就新增一条记录。

记录原则：
- 一条记录只描述一个问题。
- 尽量写清楚页面、操作路径、预期结果和实际结果。
- 如果有截图，把截图放到 `docs/assets/trial-issues/`，并在记录里引用相对路径。
- 如果不确定是不是 bug，也先记录，状态标为 `待确认`。

建议截图命名：

```text
docs/assets/trial-issues/ISSUE-001-short-title.png
docs/assets/trial-issues/ISSUE-002-short-title.png
```

状态枚举：
- `待确认`：现象已记录，但还没判断是 bug、设计边界还是数据问题。
- `待修复`：已确认需要修。
- `修复中`：正在修改。
- `待验证`：代码已改，等待浏览器确认。
- `已完成`：已验证通过。
- `暂缓`：确认不是当前试运行必须处理。

优先级枚举：
- `P0`：阻塞试运行或可能导致数据错误。
- `P1`：影响主要业务判断或日常使用效率。
- `P2`：体验问题，不阻塞主流程。
- `P3`：优化建议。

问题类型：
- `字段映射`：UI 字段和数据库/API 字段不一致。
- `阶段/状态`：卡片、筛选、状态流转不一致。
- `权限`：不同角色看到或能操作的内容不符合预期。
- `数据刷新`：保存后列表、计数、卡片没有及时更新。
- `交互体验`：入口、按钮、弹窗、表单不好用或容易误解。
- `视觉布局`：遮挡、溢出、对齐、响应式问题。
- `数据治理`：坐标、联系人、重复客户、导入导出等数据质量问题。
- `其他`：不属于以上类型。

### ISSUE-001：保存 Deal 信息后卡片阶段未实时推进

- 状态：已完成
- 优先级：P1
- 问题类型：阶段/状态
- 页面/模块：Follow-up / Deal / Lead Detail
- 角色/账号：Leader
- 相关记录：JPT-2604-0001
- 发现日期：2026-05-01
- 截图：用户会话截图

**操作步骤**
1. 打开 `Follow-up` 模块。
2. 打开某条 lead 的详情。
3. 切换到 `Deal` tab。
4. 填写报价号、PO 号、合同金额等 deal 信息。
5. 点击 `Save Changes`。

**预期结果**

保存后卡片阶段应根据 deal 信息推进，例如报价信息推进到 `Quoted`，PO 或合同金额推进到 `Won`。

**实际结果**

保存成功，但当前模块卡片仍显示旧阶段。

**初步判断**

后端没有根据 deal 证据推进 `sales_stage`，前端保存后也没有等待当前模块刷新完成。

**对应字段/API**

- `PATCH /api/leads/{id}`
- `sales_stage`
- `quotation_id`
- `quotation_date`
- `po_number`
- `po_date`
- `deal_amount`

**处理记录**
- 2026-05-01：新增后端自动阶段推进规则：报价证据推进到 `Quoted`，PO/PO 日期/正数合同金额推进到 `Won`。
- 2026-05-01：前端 `Save Changes` 后等待 `refreshAllCounts()` 完成。
- 2026-05-01：回归脚本从固定 4 条 lead 改为动态数量校验。

**验证结果**

- 阶段推进临时库测试通过。
- 浏览器 full 回归通过。

### ISSUE-009：Follow-up 统计与状态刷新不同步

- 状态：已完成
- 优先级：P1
- 问题类型：数据刷新
- 页面/模块：Follow-up / Lead Detail
- 角色/账号：Leader
- 相关记录：JPT-2605-0001、Follow-up 列表卡片

- 截图：`docs/assets/trial-issues/ISSUE-009-short-title.png`

**操作步骤**
1. 打开 `Follow-up` 模块。
2. 打开某条 lead 的右侧详情。
3. 在 `Follow-ups` tab 添加新的 follow-up。
4. 保存后观察右侧记录状态、中间卡片次数、左侧导航计数。

**预期结果**

新增正式 follow-up 后，新记录状态应使用表单选择值，默认是 `pending`；该 lead 应进入或保持 `Following` 阶段；右侧记录数、中间卡片 `Follow-ups` 次数、左侧 `Follow-up` 计数应同步更新。

**实际结果**

新增记录被自动显示为 `completed`；中间卡片 `Follow-ups` 次数仍为 0；有 follow-up 记录的 `New` lead 仍停留在 `New`，导致左侧 `Handler` 与 `Follow-up` 计数不符合实际工作流。

**初步判断**

Follow-up activity 没有保存 `status/response_date`；Lead 列表 API 没有返回正式 follow-up 数量；新增 follow-up 后没有把 `New/Assigned` lead 推进到 `Following`；旧数据中已经存在 follow-up 的 lead 也缺少阶段修复。

**对应字段/API**

- `POST /api/leads/{id}/activities`
- `GET /api/leads`
- `lead_activities.action_type = follow_up`
- `leads.sales_stage`
- `leads.next_followup_date`

**处理记录**
- 2026-05-03：Activity API 增加 `status` 与 `response_date` 入参，并写入 `payload_json`。
- 2026-05-03：新增正式 follow-up 后，若 lead 仍是 `New/Assigned`，自动推进到 `Following`。
- 2026-05-03：启动时自动修复旧数据：已有 active follow-up 的 `New/Assigned` lead 推进到 `Following`。
- 2026-05-03：Lead 列表返回 `follow_ups_count`，卡片次数改为读取真实 active follow-up 数量。
- 2026-05-03：导航计数抽成统一派生函数，Dashboard 与保存刷新共用同一套口径。
- 2026-05-03：Follow-up 模块只显示 `Assigned/Following` 工作列表，避免 `New` lead 同时出现在 Handler 和 Follow-up。
- 2026-05-03：保存/归档 follow-up、after-sales 后等待刷新完成，避免右侧已保存但左侧/中间仍是旧数字。

**验证结果**

2026-05-04 自动 full 回归通过：
- Dashboard `Following=2`，左侧 `Follow-up=2`。
- Follow-up 默认列表 2 张卡片，阶段均为 `Following`。
- Follow-up 卡片次数来自真实 activity：当前为 `3 / 1`。
- 新增 follow-up 保持表单状态 `pending`，不会自动变成 `completed`。
- 测试 follow-up 已归档清理。
